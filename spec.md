# Messaging Client Specification

**Version:** 1.0

## 1. Purpose

This specification defines the behavior and network protocol for a local messaging system consisting of:

* A messaging server
* An iOS client
* An Android client

The clients are independent implementations. They must conform to the same protocol and behavioral requirements.

The specification is authoritative for client behavior. Platform-specific implementation details may differ between clients as long as externally observable behavior conforms to this specification.

---

# 2. Environment

The system runs locally.

The server may maintain all state in memory.

No external services are required.

The server is not required to persist data across server restarts.

Clients must persist their own required offline state across application restarts.

---

# 3. User Identity

## 3.1 First launch

On first launch, the client must request a user name.

The user name:

* Must be non-empty.
* Must be persisted locally by the client.
* Identifies the user for the lifetime of the local client installation.

## 3.2 Subsequent launches

On subsequent launches, the client must restore the previously stored user name without requiring the user to enter it again.

## 3.3 Server identification

After establishing a WebSocket connection, the client must identify itself to the server.

Example:

```json
{
  "type": "identify",
  "userId": "alice"
}
```

The server responds:

```json
{
  "type": "identified",
  "userId": "alice"
}
```

---

# 4. Message Model

A message contains:

| Field             | Description                                       |
| ----------------- | ------------------------------------------------- |
| `serverMessageId` | Unique identifier assigned by the server          |
| `clientMessageId` | Unique identifier generated by the sending client |
| `senderId`        | User who created the message                      |
| `recipientId`     | Intended recipient                                |
| `body`            | Text content                                      |
| `createdAt`       | Server-assigned creation timestamp                |

The message body is plain text.

The initial protocol does not support attachments, reactions, editing, deletion, or group conversations.

---

# 5. Client Message IDs

Each outgoing message must receive a unique `clientMessageId` before transmission.

The ID must remain unchanged across retries.

If a message is transmitted multiple times because of network failure, every retry must use the same `clientMessageId`.

The client must persist the `clientMessageId` with the outgoing message.

---

# 6. Server Message IDs

When the server accepts a new message, it assigns a unique `serverMessageId`.

The server must associate the `serverMessageId` with the corresponding `clientMessageId`.

If the server receives a duplicate `clientMessageId` from the same sender, it must not create a second message.

Instead, it must return the previously assigned `serverMessageId`.

This makes sending idempotent.

---

# 7. Sending Messages

A user may compose a text message addressed to another user.

The client creates a new outgoing message with:

* `clientMessageId`
* recipient
* body
* local pending state

The message must be persisted locally before the client considers the message eligible for transmission.

If the client has an active connection, it should attempt transmission immediately.

If no connection is available, the message remains in the local outgoing queue.

---

# 8. Outgoing Queue

The client maintains a durable outgoing queue.

Messages remain in the outgoing queue until the server has acknowledged acceptance.

A temporary network failure must not cause a queued message to be discarded.

The queue must survive application termination and relaunch.

When a connection becomes available, the client must attempt to transmit all pending outgoing messages.

A message must retain the same `clientMessageId` across retries.

---

# 9. Server Acceptance

The server accepts a message using the following request:

```json
{
  "type": "send",
  "clientMessageId": "abc-123",
  "recipientId": "bob",
  "body": "Hi Bob"
}
```

For a newly accepted message, the server responds:

```json
{
  "type": "sendAccepted",
  "clientMessageId": "abc-123",
  "serverMessageId": "server-987"
}
```

After receiving `sendAccepted`, the sender may remove the corresponding message from its outgoing queue.

If the client does not receive the acceptance response, it must retain the message and retry after reconnecting.

---

# 10. Message Delivery

When the server has a message for a recipient who is not currently connected, the server must retain the message in memory.

When the recipient connects, the server must deliver pending messages.

The server must retain an undelivered message until the recipient acknowledges receipt.

---

# 11. Receiving Messages

A client receives messages using:

```json
{
  "type": "message",
  "serverMessageId": "server-987",
  "clientMessageId": "abc-123",
  "senderId": "alice",
  "recipientId": "bob",
  "body": "Hi Bob",
  "createdAt": "2026-09-29T20:00:00Z"
}
```

The receiving client must:

1. Check whether the `serverMessageId` has already been processed.
2. If it has already been processed, it must not create a duplicate visible message.
3. If it is new, persist the message locally.
4. Make the message available to the UI.
5. Send an acknowledgement to the server.

The acknowledgement is:

```json
{
  "type": "ack",
  "serverMessageId": "server-987"
}
```

The client should persist the message before acknowledging it.

---

# 12. Duplicate Delivery

The protocol provides at-least-once delivery.

A message may be delivered more than once if a connection fails during delivery.

Clients must deduplicate messages using `serverMessageId`.

A duplicate delivery must not create a second visible message.

---

# 13. Reconnection

A client must detect when its connection is no longer usable.

When connectivity becomes available again, the client must:

1. Establish a new WebSocket connection.
2. Identify itself.
3. Resume transmission of pending outgoing messages.
4. Receive pending incoming messages from the server.
5. Continue normal operation.

Reconnection must not require the user to manually resend previously queued messages.

---

# 14. Connection Loss During Sending

If a client sends a message and the connection is lost before receiving `sendAccepted`, the client must assume that the server may or may not have received the message.

The client must retain the message in its outgoing queue.

When the connection is restored, the client must retry using the same `clientMessageId`.

The server must treat duplicate submissions of the same `clientMessageId` as the same logical message.

This prevents duplicate server-side messages.

---

# 15. Connection Loss During Receiving

If a client receives a message but loses its connection before sending an acknowledgement, the server may deliver the message again after reconnection.

The client must deduplicate the message using `serverMessageId`.

The second delivery must not create a duplicate visible message.

---

# 16. Server Behavior

The server maintains:

* Registered users
* Active WebSocket connections
* Accepted messages
* Undelivered messages

The server may store all state in memory.

The server does not need to persist state across server restarts.

The server must support multiple simultaneous connected clients.

A message addressed to an unknown user must be rejected.

---

# 17. Protocol Errors

Errors must use the following structure:

```json
{
  "type": "error",
  "code": "ERROR_CODE",
  "message": "Human-readable description"
}
```

The protocol must define errors for at least:

* Unknown recipient
* Invalid message
* Invalid identity
* Unsupported protocol message

An error must not cause the client to silently discard a durable outgoing message unless the error indicates that retrying the message cannot succeed without user intervention.

---

# 18. Ordering

For messages sent by the same sender to the same recipient, the server should preserve acceptance order.

Clients must not assume that messages from different senders are globally ordered.

The server-assigned `createdAt` timestamp represents the server's observed message creation time.

---

# 19. Required User Scenarios

## Scenario 1 — Online message

Given Alice and Bob are connected.

When Alice sends:

> Hi Bob, I have something important to tell you

Then Bob must receive exactly one corresponding message.

---

## Scenario 2 — Reply

Given Bob has received Alice's message.

When Bob sends:

> What is it?

Then Alice must receive exactly one corresponding message.

---

## Scenario 3 — Alice goes offline

Alice loses connectivity.

Alice sends a message to Bob.

The message must be persisted in Alice's outgoing queue.

Bob must not receive the message while Alice remains unable to transmit it.

---

## Scenario 4 — Bob goes offline

Bob loses connectivity.

Bob sends a message to Alice.

The message must be persisted in Bob's outgoing queue.

---

## Scenario 5 — Alice reconnects

Alice reconnects.

Alice's pending outgoing message must be transmitted.

The server must accept it exactly once.

Bob may still be offline.

The server must retain the message for Bob.

---

## Scenario 6 — Alice disconnects again

Alice loses connectivity again.

Her client must remain capable of receiving previously delivered messages when connectivity is restored.

---

## Scenario 7 — Bob reconnects

Bob reconnects.

The server must deliver Alice's pending message to Bob.

Bob must persist and display the message and acknowledge it.

Bob's previously queued outgoing message must also be transmitted.

Alice must receive Bob's message after she reconnects.

---

# 20. Persistence Requirements

The clients must persist enough state to survive application termination.

At minimum:

### Identity

The user's identity.

### Outgoing messages

Messages that have not received server acceptance.

### Received messages

Messages that have already been successfully received.

### Deduplication state

Enough information to recognize previously processed `serverMessageId` values.

The exact persistence technology is platform-specific.

The specification does not require a particular database or storage framework.

---

# 21. Platform Independence

The following behavior must be identical across clients:

* Identity semantics
* Message structure
* Message IDs
* Sending semantics
* Server acknowledgement semantics
* Offline queue semantics
* Reconnection behavior
* Delivery semantics
* Deduplication behavior
* Error semantics

The following may be platform-specific:

* UI framework
* Local persistence implementation
* WebSocket library
* Concurrency model
* Application lifecycle integration
* Dependency injection mechanism
* Testing framework

---

# 22. Non-Goals

Version 1 does not require:

* Authentication
* Encryption
* Cloud deployment
* Push notifications
* Message search
* Attachments
* Images
* Reactions
* Message editing
* Message deletion
* Group conversations
* Read receipts
* Typing indicators
* Server persistence across restarts
* Production-grade security
* Production scalability

These features may be addressed in future specification versions.
